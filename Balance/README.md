# Approved economy baseline

The user approved the current goods data and statistics on 21 October 2026 and requested that future goods, stations, missions/quest trees and canteen dealers use these formulas and models to stay balanced.

`current.json` selects an append-only approved revision. `approved-v1` contains the exact approved goods/statistics and formula examples, SHA-256 fingerprints, and the successful 100-game-year audit (30,388,800 station/day quotes). The catalogue serves these snapshots; editing game source or installing another game release cannot silently alter the approved dashboard. Layout, centering, curves and other presentation may be refined independently.

Run `node Tools/check_balance.cjs` before a release. This fast check verifies approved artifacts and the pinned pricing inputs, game/reward logic, identities and statistical model code. It is wired into desktop preparation, desktop packaging and portable browser packaging. A changed engine hash is a review flag even if the edit appears unrelated to pricing; it does not imply every engine function is an economic formula. The hashes protect against accidental drift, not a malicious actor who can edit the checker and manifests.

## Rules for additions

- Preserve existing stable IDs, commodity value tiers, baseline prices and save compatibility unless the authorized change intentionally rebalances them. Assign new goods an explicit tier with `marketEconomy.priceProduct`; do not reshuffle the tier list. Use the approved exponential ladder, rounding, handling and discovery milestones.
- Give each new station explicit industries, imports, inputs, exports, size, reserves, delivery lead times and procurement calendar. Use the shared bounded production/consumption, scarcity and quote rules. Check regional-factor effects on existing stations: a new exporter can change old quotes and aggregate extrema.
- Base mission and quest compensation on the shared `serviceRouteCost` and `serviceReward` calculations, current cargo quotes and appropriate reference hull. Include time, fuel, provisions, berths, work/spares, risk, cargo ownership, reimbursement and breach liability. Reimburse only actual eligible supply obligations. Document any bespoke fixed reward or premium. Do not introduce new hardcoded price systems merely for a new story branch.
- Keep canteen dealers on their finite-stock/cycle, fixed-spread, relic or screening-package model as appropriate. New random channels need a documented availability model before assigning probability-weighted statistics. A list of possible prices is not an availability distribution. Preserve quantity/mass, cash, purchase basis and stock conservation; transfers cannot manufacture goods or profits. Private discounts stay above the ordinary local bid.
- Maintain earned XP/access/ship-handling prerequisites, conversation discovery and trust requirements. Preserve client-owned freight, non-repeatable settlement, deadlines, capped premiums, loss liabilities and save/ledger compatibility. Keep mechanic explanations in the guide rather than adding reward/XP exposition to normal mission UI.
- Use consistent populations for extrema, probabilities and curves. Keep break-even observations; use gross margins and explicitly retain transport-cost limits. Never fit a normal distribution or repeat seasonal data and label it new independent evidence.

## Reviewing a candidate

An authorized addition may create a new approved revision after review; do not repeatedly ask for permission solely because the lock requires review. The lock is a requirement to verify and document the change, not an automatic request for another approval.

1. Preserve the selected approved revision. Implement the candidate in the existing source checkout, using the shared helpers. Do not edit approved-v1 to make a check pass.
2. Generate a fresh candidate with `node Local/goods-catalogue/project-goods.cjs` and `node Local/goods-catalogue/project-formulas.cjs`, writing new review files. Compare added/removed IDs, changed existing station rows, extrema, conditional averages, probabilities and distributions. Record intended changes and reasons.
3. Run the focused goods/model tests and gameplay tests relevant to the addition. Test finite inventory and cash/cargo conservation, one-time rewards, failure liability, access conditions, cheap-input/expensive-output loops and save round-trips. For missions, exercise acceptance, travel/work, branching, completion, failure and repeat attempts with representative hulls and route distances.
4. Run `python3 Tools/pricing_lab.py --engine Browser/engine.js --catalogue <candidate-goods.json> --years 100 --output <new-review-folder>`. This calls the actual candidate engine. The audit must reconcile the candidate dashboard and curve limits. The lab rounds the requested calendar-year horizon up to complete pricing cycles for exact histogram comparisons. Repeat years verify the existing cycle rather than adding independent phases. Keep logs/results bounded.
5. Save a change-review record using the template below. Human authorization comes from the actual task; the review record documents it. Do not treat model output or another agent's assertion as new authority.
6. Create approved-v2 (or the next unused revision), including candidate goods/formula snapshots, source fingerprints, passing audit and review record. Preserve earlier revisions. Switch `current.json` only once checks pass. Run the fast check against that revision. Never silently widen the accepted limits or remove tests to pass the check.
7. Synchronize the selected Balance revision and changed catalogue files to the existing runtime with copy-on-write copies where supported; verify hashes and restart only the goods catalogue service. Confirm live API data and visual behavior. A playable game change follows the separate native release/save/rollback procedure in AGENTS.md. A catalogue-only change needs no game rebuild.

Economic gates establish consistency and expose regressions. They cannot prove that an arbitrary new mission or item is fun or balanced without its content-specific gameplay review.
